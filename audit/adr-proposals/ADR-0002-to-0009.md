# Proposed ADRs 0002–0009

Each follows Context · Decision · Consequences · Alternatives. Status: Proposed (2026-09-29, audit of `91c48ad`).

---

## ADR-0002 — SQLite as system of record: integrity pragmas, schema versioning, relative paths

**Context.** SQLite is declared authoritative (ADR-0001) but runs with `foreign_keys=OFF`, rollback journal, no schema version, absolute paths, and additive `ALTER TABLE` in `init_db`. A restore to another path fails every check; the ORM insert order violates the declared FKs (AUD-027/041/042).
**Decision.** Every connection sets `foreign_keys=ON`, `busy_timeout`, deferred FK checks within explicit transactions; `PRAGMA user_version` tracks schema; numbered, tested migrations; new rows store paths relative to the workspace root (existing absolute rows rebased by `kdp relocate`); `.backup` API for backups.
**Consequences.** Older code refuses newer DBs; migrations need tests from each tag; one-time rebase of existing rows.
**Alternatives.** Keep absolute paths + relocate tool only (cheaper; still fragile across OSes).

## ADR-0003 — Workspace identity: authenticate at the proxy

**Context.** Human approvals are form posts with a typed name; the only token is process-global (AUD-001). Staging exposes the Workspace to a tailnet via Caddy (AUD-002).
**Decision.** Identity comes from an authenticating proxy (Tailscale identity or forward/basic auth) via a trusted header accepted only from loopback; the app maps identity → operator and roles (`author`, `reviewer`, `admin`); `actor_id` is always the authenticated identity; name fields are removed; release approval requires a reviewer different from the preparer (SoD).
**Consequences.** Loopback dev keeps working with a configured single local identity; staging requires proxy config in the repo.
**Alternatives.** App-level login with sessions (more code, password storage); client certificates.
